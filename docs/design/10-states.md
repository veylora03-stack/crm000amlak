# حالت‌های صفحات — CRM تخصصی املاک

این سند حالت‌های استاندارد هر صفحه را تعریف می‌کند. هیچ صفحه‌ای نباید بدون حالت‌های Loading، Empty، Error، No Permission، Validation Error، Success و Unsaved Changes پیاده‌سازی شود. اگر حالتی برای صفحه‌ای واقعاً کاربرد ندارد، باید رفتار جایگزین آن به‌صورت صریح تعریف شود.

---

## 1. تعریف حالت‌های استاندارد

### Loading
- برای داده‌های اولیه باید Skeleton نمایش داده شود.
- برای اقدامات دکمه‌ها باید Spinner نمایش داده شود.
- در حالت Loading نباید امکان ارسال مجدد فرم وجود داشته باشد.
- Skeleton باید اندازه واقعی محتوا را شبیه‌سازی کند.
- در جدول‌ها باید Skeleton ردیف‌ها نمایش داده شود.

### Empty
- باید شامل آیکون، عنوان فارسی، توضیح کوتاه و در صورت نیاز دکمه اقدام باشد.
- نباید با خطا اشتباه گرفته شود.
- برای لیست‌های خالی، جستجوی بدون نتیجه، Dashboard خالی و Timeline خالی استفاده شود.
- در Empty State باید کاربر بداند چه کاری باید انجام دهد.

### Error
- باید شامل پیام فارسی، آیکون و دکمه تلاش مجدد باشد.
- نباید جزئیات فنی حساس یا Stack Trace نمایش داده شود.
- خطای سرور باید به‌صورت Error State یا Alert نمایش داده شود.
- خطای Validation باید زیر فیلد مرتبط برود.
- برای خطاهای غیرمنتظره باید یک پیام عمومی امن نمایش داده شود.

### No Permission
- باید شامل پیام واضح، آیکون قفل و دکمه بازگشت باشد.
- نباید اطلاعات حساس صفحه را حتی به‌صورت Skeleton نشان دهد.
- برای کاربران غیرمجاز باید قبل از دریافت داده نمایش داده شود.
- در Router Guard و API باید همزمان کنترل شود.

### Validation Error
- باید به‌صورت فارسی و در کنار فیلد مرتبط نمایش داده شود.
- باید فوکوس به اولین فیلد دارای خطا برود.
- نباید فرم در حالت خطا بسته شود.
- باید خطاهای سمت سرور با ساختار استاندارد API نمایش داده شوند.
- برای فرم‌های طولانی باید خلاصه خطاها نیز نمایش داده شود.

### Success
- باید با Toast موفقیت نمایش داده شود.
- در صورت نیاز باید کاربر به صفحه بعدی هدایت شود.
- نباید Toast بیش از حد طولانی باشد.
- برای عملیات مهم مانند ذخیره، حذف نرم، خروجی‌گیری و تغییر Stage باید پیام موفقیت داشته باشد.
- در Kanban، موفقیت جابجایی می‌تواند به‌صورت Toast کوتاه یا تغییر بصری باشد.

### Unsaved Changes
- باید فرم‌های دارای تغییرات ذخیره‌نشده را تشخیص دهد.
- قبل از بستن Modal یا Drawer باید تأیید گرفته شود.
- قبل از ترک صفحه با Router باید تأیید گرفته شود.
- برای فرم‌های طولانی می‌توان از Autosave کنترل‌شده استفاده کرد.
- پیام باید فارسی باشد: «تغییرات ذخیره‌نشده دارید. آیا مطمئن هستید؟»

## 2. اولویت نمایش حالت‌ها

هر صفحه باید حالت‌ها را با این اولویت بررسی کند:

1. No Permission
2. Error
3. Loading
4. Empty
5. Data
6. Validation Error به‌صورت محلی روی فرم
7. Success Toast به‌صورت سراسری

### قاعده کلی
- اگر کاربر دسترسی ندارد، No Permission نمایش داده شود.
- اگر دسترسی دارد اما داده خطا داد، Error نمایش داده شود.
- اگر داده در حال دریافت است، Loading نمایش داده شود.
- اگر داده دریافت شد ولی خالی بود، Empty نمایش داده شود.
- اگر داده داشت، محتوای اصلی نمایش داده شود.

## 7. حالت No Permission

### الگوی نمایش
- آیکون قفل
- عنوان: «دسترسی ندارید»
- توضیح: «برای مشاهده این بخش باید دسترسی مناسب داشته باشید.»
- دکمه‌ها:
  - «بازگشت»
  - «رفتن به داشبورد» در صورت نیاز

### قواعد
- No Permission باید قبل از Loading نمایش داده شود.
- نباید درخواست API برای داده‌ای که کاربر اجازه دیدن آن را ندارد ارسال شود.
- برای صفحاتی که فقط Admin دسترسی دارد، باید Router Guard داشته باشد.
- برای رکوردهای خاص مانند مشتری یا ملک دیگران، باید سطح رکورد نیز کنترل شود.

## 8. حالت Validation Error

### الگوی نمایش
- Border قرمز برای فیلد
- آیکون خطا در صورت نیاز
- پیام فارسی زیر فیلد
- فوکوس به اولین فیلد خطا

### نمونه پیام‌ها
- «این فیلد الزامی است.»
- «شماره موبایل معتبر نیست.»
- «ایمیل تکراری است.»
- «مبلغ باید عدد مثبت باشد.»
- «تاریخ سررسید نمی‌تواند در گذشته باشد.»
- «حجم فایل بیشتر از 10 مگابایت است.»
- «فرمت فایل مجاز نیست.»

### قواعد
- پیام‌ها باید کوتاه و فارسی باشند.
- نباید پیام فنی مانند Exception نمایش داده شود.
- خطاهای سمت سرور باید به فیلد مرتبط نگاشت شوند.
- اگر خطا به فیلد خاصی مرتبط نبود، به‌صورت Alert نمایش داده شود.

## 9. حالت Success

### الگوی نمایش
- Toast سبز با آیکون موفقیت
- پیام کوتاه فارسی
- بسته شدن خودکار بعد از 3 تا 5 ثانیه

### نمونه پیام‌ها
- «مشتری با موفقیت ذخیره شد.»
- «ملک با موفقیت ذخیره شد.»
- «معامله به مرحله جدید منتقل شد.»
- «وظیفه انجام شد.»
- «خروجی گزارش آماده شد.»
- «تنظیمات ذخیره شد.»

### قواعد
- Success نباید مانع ادامه کار کاربر شود.
- برای عملیات خطرناک یا مهم می‌توان Success را با Undo همراه کرد.
- برای جابجایی Deal در Kanban، اگر Undo لازم نیست، Toast کوتاه کافی است.
- اگر عملیات ناموفق بود، نباید Success نمایش داده شود.

## 10. حالت Unsaved Changes

### موارد نیازمند تأیید
- فرم ایجاد یا ویرایش مشتری
- فرم ایجاد یا ویرایش ملک
- فرم ایجاد یا ویرایش Deal
- فرم تعامل
- فرم وظیفه
- فرم تنظیمات
- فرم پروفایل
- فرم مدیریت کاربران

### الگوی Confirm
- عنوان: «تغییرات ذخیره‌نشده»
- توضیح: «اگر این صفحه را ترک کنید، تغییرات ذخیره‌نشده از بین می‌رود.»
- دکمه‌ها:
  - «ماندن»
  - «ترک صفحه»
  - «ذخیره» در صورت امکان

### قواعد
- Modal یا Drawer نباید بدون تأیید بسته شود.
- Router Navigation باید قبل از ترک صفحه تأیید بگیرد.
- اگر فرم Autosave دارد، باید وضعیت Autosave مشخص باشد.
- برای فرم‌های خیلی کوتاه مانند جستجو یا فیلتر، تأیید لازم نیست.

## 11. حالت‌های ترکیبی

### Loading + Error
- اگر Skeleton اولیه خطا داد، Error State جایگزین Skeleton شود.
- اگر بخش‌هایی خطا دادند، فقط همان بخش‌ها Error State شوند.

### Empty + Search
- اگر جستجو نتیجه نداشت، Empty State مخصوص جستجو نمایش داده شود.
- باید دکمه «پاک کردن جستجو» داشته باشد.

### Empty + Filter
- اگر فیلترها نتیجه نداشتند، Empty State مخصوص فیلتر نمایش داده شود.
- باید دکمه «حذف فیلترها» داشته باشد.

### Error + Validation
- خطای سرور عمومی با Alert نمایش داده شود.
- خطای فیلدها با Validation Error نمایش داده شود.
- نباید هر دو حالت کاربر را گیج کنند.

### Success + Unsaved Changes
- بعد از Success، وضعیت dirty فرم پاک شود.
- Modal یا Drawer فقط بعد از Success بسته شود.
- اگر Success همراه با Redirect است، Unsaved Changes باید قبلاً پاک شده باشد.
